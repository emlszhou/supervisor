# 全本地模型运行手册：防卡住、防误验收、保留现场

日期：2026-10-04（Asia/Shanghai）。配合 [执行规划](LOCAL-MODEL-EXECUTION-PLAN.md) 使用。

这是开发阶段的操作规则，不是已经实现的自动Supervisor。当前仍先完成M1；M2隔离和M3自动编排尚未通过验收。以下步骤由本地Coordinator和确定性工具核对，不能仅由模型口头承诺。

## 1. 先解决最容易出错的五件事

1. **真实新会话**：同一聊天里说“现在我是Reviewer”不算fresh；不能拿实现聊天的摘要、隐藏会话记忆或实现者的chain-of-thought代替独立输入。必须有实际不同会话/进程记录，Reviewer重新读取合同和候选。
2. **真实命令证据**：没有退出码和本轮收集数，不写“测试通过”。测试没跑、输出截断、报告过期或只跑了子集就如实标记。
3. **没有隐式重试**：服务断线、限额、进程超时或上下文满时，先核对实际副作用。已经启动的操作可能仍在运行，不能再启动一份。
4. **不会偷偷改题**：改测试、放宽预算、缩小平台范围、换task ID或增加角色不能用来规避失败。实现者只能提明确变更，协调者走规格流程，保留旧失败。
5. **停止是真停止**：到blocked/reject/额度耗尽就保存现场和缺失条件。不要继续后台运行、另开分支无限修补或假装下一里程碑能掩盖当前失败。

## 2. 每次启动的 preflight

在调用本地模型之前记录真实值：

| 检查 | 必须核对的证据 | 不符合时 |
| --- | --- | --- |
| 仓库/分支/角色 | 实际Git根、remote身份、branch、HEAD、role | 停止错误角色操作，不靠目录名字猜 |
| 合同 | 外部路径、spec完整SHA、manifest摘要、task/run/attempt | 停止；不能从实施目录复制一份“新合同” |
| 基线 | 合同baseline可解析，初始kickoff精确匹配；已有候选按祖先关系检查 | 不reset旧工作；先报告实际状态 |
| 工作区 | staged、unstaged、untracked与正在运行操作均可解释 | 保留文件；不clean或无范围git add |
| 本地端点 | 服务可达、实际模型名/版本、无云fallback、当前role路由 | 明确ENVIRONMENT_FAILURE，不能切云兜底 |
| 会话 | 实际创建的会话ID/进程，Reviewer未参与实现 | 不能证明fresh则不启动accept审核 |
| 工具 | Python/uv/Git、frozen锁安装、doctor | 诊断缺失前提，不升依赖/关闭校验 |
| 资源 | 可用内存/磁盘、已加载模型、当前任务wall预算 | 顺序执行；不足停止，不猜适配容量 |
| 授权 | allowed/forbidden、阶段可写位置、Git/合并权限 | 路由按现有授权，无新增权限自行批准 |

检查控制目录、权重/日志目录不会被提交。不要输出完整环境变量或认证文件。模型端点发现只记录地址类型和模型标识，不复制密码、token或请求正文。

M1包中的42项是缺实现基线，现有完整项目194项是已集成M0；这两个数字不能混写成“M1已通过”。后续提交测试数变化时以本轮实际收集为准。

## 3. 让角色切换成为真实操作

正确流程：

1. Implementer停止写入、提交允许文件、推送并给出最后tip完整SHA。
2. Coordinator固定该SHA，创建独立Reviewer检出，验证外部合同摘要。
3. 用已核验的Hermes新会话方式实际启动另一会话。若当前软件不能自主新建，就由操作者启动另一实例后粘贴Reviewer提示词；不要模拟新会话。
4. 交给Reviewer的材料：用户目标、冻结合同、精确候选、必要公开接口、上一轮findings。实现报告是待验证线索。
5. Reviewer使用自己的检查记录，输出schema-valid review；不修改候选生产代码。
6. `reviewer.session_id`来自实际会话标识；软件不暴露时记录独立启动的本地run/session映射并说明来源，不编造软件原生ID。
7. 最终验收另起会话。若Reviewer参与代码修改，它成为Implementer，不能签发该候选accept。

同模型新会话仍可能重复同一错误。固定保护验收、独立故障注入和权限边界不能省略。

## 4. 执行与日志：判断“做过了”的依据

每个检查都保存结构化元数据：argv数组、cwd、开始/结束时间、实际exit code、收集/通过/失败/跳过数、绑定candidate/bundle。原始测试输出默认只留本机受控目录，提交摘要和必要脱敏复现。

- 使用进程工具真实等待完成，不把后台PID存在当测试成功。
- 不用`pytest ... | tail ...`后的最后命令状态冒充pytest退出码；抓日志必须保留原runner的exit code。
- 读取JUnit时核对它是本次生成、目标正确、收集非零，不读取旧XML来填新报告。
- 必需检查缺结果写`not_run`，不能算通过；skip/xfail与pass分别计数。
- “完整pytest”与“unit+独立验收子集”分别写准确argv。不要重复相加重叠测试声称更高通过率。
- 运行外部冻结pytest使用`python -B`或PYTHONDONTWRITEBYTECODE，避免向冻结包写bytecode；需要时禁用pytest cacheprovider，运行后再次核验包inventory。
- 故障探测必须有外部watchdog、有限输出/时间、finally清理。测试程序不能把无限输出写入内存，测试fixture自身也要能超时。
- 新增文件先看状态和范围，再按确切路径stage，不用无范围`git add .`。

## 5. 心跳、超时、取消与断线

开发操作建议每5分钟更新一次控制面状态：阶段、最后真实进展、当前操作ID/PID、已用wall时间、下一检查。这个心跳用于发现卡住，不增加合同预算，也不自动证明成功。

wall上限使用当前冻结任务的值：M1为7200秒（2小时），包括此run的持续工作；不能每开一个模型会话就重置。耗尽保存状态并停止。模型服务请求超时、Agent命令超时、单个测试watchdog与整个任务wall是不同限制，要分别记录。

长时间没有新输出：

1. 查实际进程/服务状态、CPU/内存、文件变化与已有完成证据。
2. 活跃且身份对应：等待至既定预算或显式取消，不启动重复操作。
3. 取消只作用于本任务记录的进程与可确认后代，先按已核验Agent/Worker协议执行，再检查退出、管道和资源。
4. 无法确认回收则写false/unknown，停止后续操作。leader退出不等于整棵树停止。
5. 不执行范围不明的`pkill python`/`killall`，不杀本地推理服务或用户其他进程。

模型服务断线或OOM：保留已生成代码，记录ENVIRONMENT_FAILURE。只有证明操作没启动或没有副作用时才可安全重试；其他情况进入NEEDS_HUMAN。诊断后可以恢复同一合同的工作，但总时间、返修与接管额度不重置。

基础设施问题不能伪装成“业务验收失败”；业务失败也不能用重启服务把失败记录抹掉。

## 6. 崩溃/上下文满后的恢复

不使用聊天记忆作为唯一进度。Coordinator在实施目录之外保存状态，可用 [状态记录模板](../templates/local-run-status.json)。它是运维sidecar示例，不是已有Supervisor数据库schema或已实现恢复引擎。

恢复顺序：

1. 读取last state，fetch分支，核对合同/基线/候选SHA和未提交文件。
2. 查询上一operation的实际进程和完成证据；若它可能还在执行，禁止第二次启动。
3. 完成证据匹配且结果齐全：幂等导入；不能重新执行。
4. 正在运行：重连或明确报告running；不复制一份Agent。
5. 工作区变了但完成证据缺失：NEEDS_HUMAN，列出未提交文件和不能确认的副作用。
6. pending/unknown数据库记录只说明记录状态；不得把它解释成“从没调用模型”。
7. 上下文满需要续接时，固定新会话、保存下一步骤和真实证据；实现续接不等于新任务，不重置额度。Reviewer不能续接实现会话来完成fresh审核。

模板中的side_effects_confirmed=false只表示没有确认，不表示“确认没发生副作用”。unknown不能重放；必须有确定的无副作用证据、仍在预算内并签发新的attempt后才允许重试。replay_allowed默认false，不由模型自行改true取得权限。

私有状态文件应原子更新（同目录临时文件后rename），不覆盖最后可靠记录；进程/机器崩溃后若写入不确定，先核验而非盲信JSON。

## 7. 单写入者与Git冲突

同一实施目录同一时刻只有一个写入角色。当前Coordinator串行启动；不要认为Git分支或目录名就是跨进程锁。自动锁/抢占/租约的可靠实现留给后续编排任务验证。

- 审核独立克隆精确提交，不在实现者正在写的目录中验收。
- push前fetch，确认远端实现分支仍是自己预期的父提交；其他人更新时不覆盖、不强推。
- 普通pull用`--ff-only`；分叉保留两边，记录SHA并停止依赖工作。
- 新角色不checkout/merge用户脏目录。要独立目录时新clone，不清空旧目录。
- Git冲突需要改代码时，新代码必须重新验收；不能套用冲突前accept。
- 写完审核报告不merge/cherry-pick到受限实现分支。实现者用`git show <reviewSHA>:<reportPath>`读findings。
- 依赖/lock/schema/API更新必须走规格权限，不因为import失败就升级整个环境。

## 8. 什么情况允许继续，什么情况必须停

| 情况 | 正确动作 |
| --- | --- |
| 已授权本仓库正常fetch/commit/push | 按范围继续，不每轮重复询问 |
| Reviewer首次发现业务缺陷且额度未用 | 一次性汇总return_once，不零散无限追加返修 |
| Review-2仍失败且可在同合同范围接管 | 一次takeover，随后fresh final验收 |
| Final拒绝或额度耗尽 | 终态停止，保留证据，不另起同问题合同重置次数 |
| 文件名未匹配allowed、修改保护输入、scope预算超限 | 停止越界路径，记录POLICY_VIOLATION/SCOPE_EXPLOSION |
| 冻结规格有矛盾或保护测试有确证错误 | 提规格变更；未经新规格批准不得在实现分支修验收 |
| 用户请求了权限扩大/合并/部署但授权范围不清 | 准备具体可审阅结果后向用户说明所需操作与原因 |
| 模型/工具只能使用云fallback | 停止；当前路由授权全本地，不切云服务 |
| 软件无法新建真正fresh会话 | 由操作者新建；不能伪造fresh_session=true |
| 无OS隔离却要求无人值守执行不可信Agent | 不升级为无人值守；保留受监督方式或补齐经实测隔离 |

这些是实际流程问题，不是用更长提示词就能保证解决。没有能力的步骤要清楚标记未实现/未验证。

## 9. 本地Reviewer至少主动问的六个问题

1. 这次检查是否真属于当前精确候选和合同？代码改过后旧报告是否失效？
2. 错误分支有没有异常资源泄漏、阻塞读取、无界内存/队列或不诚实的清理确认？
3. 输入对象有没有bool当int、unknown field、路径归一化、链接/硬链接/大小写或读期间变化漏洞？
4. 数据库重复/冲突/事务失败/恢复会不会错误推进状态或重复外部副作用？
5. 实现和测试是不是同时漏了同一个边界？需要独立有限故障注入吗？
6. 报告是不是把模拟平台、子集测试、未运行步骤或未知usage写成真实通过？

对M1重点测试：忽略但受控文件、已跟踪文件误被产物排除、删除/mode变化、父目录链接、恶意manifest类型、SQLite sidecar链接、并发写和commit失败回滚。

## 10. 给本地Coordinator的补充提示词

```text
先读LOCAL-MODEL-EXECUTION-PLAN.md和LOCAL-MODEL-RUNBOOK.md。
你不能在同一聊天里扮演Reviewer并声明fresh，也不能模拟执行命令后编造exit code。
当前仍先完成M1；只使用已核验的本地端点，禁止云fallback。
每一步核对精确合同/候选/角色，单写入者，按实际任务预算停止。
为每个操作持久化身份和真实证据；断线、上下文满或重启后先查询副作用，不盲目重跑。
缺能力就明确blocked及最小所需动作，不装作完整自动化已可用。
不能改保护验收或增加权限来取得accept，不换task ID重置返修次数。
已授权Git操作继续；额外合并/部署/扩权在准备好可审阅结果后按实际授权处理。
```

无法继续时请给出短报告：最后可靠SHA、合同摘要、实际阶段/剩余额度、正在运行或不确定的operation、已修改文件、失败命令和退出码、缺失前提、需要用户做的最小动作。不要只说“已完成”或“再试一次”。
